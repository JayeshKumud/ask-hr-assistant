**ingestion is a write path, serving is a read path — production RAG systems keep them as two separate processes that only touch each other through the vector store.**

**Why they're separated:**
- **Latency isolation** — ingestion (loading PDFs, chunking, embedding) is slow and bursty; a user asking a question should never wait on it. Coupling them (like your current "Index Policy Documents" button, which runs ingestion inside the same request-serving process) means one user's rebuild blocks or corrupts everyone else's session.
- **Blast radius** — `VectorStoreManager.reset()` wipes the whole collection before re-adding documents. If that's reachable from a button any user can click in production, one person can accidentally take the index offline for everyone mid-rebuild. In the separated model, only the ingestion pipeline has write access; serving is read-only, full stop.
- **Independent scaling** — query traffic and document-change frequency have nothing to do with each other. Serving needs to scale with *users* (more replicas under load); ingestion needs to run with a cadence tied to *how often policies change* (probably rare — HR policy PDFs don't change daily). Bundling them means you scale one for the sake of the other.
- **Consistency across replicas** — this is the one that actually forces the architectural split, not just makes it "nicer": if you ever run more than one serving replica (which your current single-pod, `ReadWriteOnce`-PVC design deliberately avoids — see the comment in `deployment.yaml`), every replica needs to read the *same* index. A local rebuild-on-click model can't guarantee that; a separate ingestion job writing to one shared store can.

**How the ingestion pipeline typically gets triggered, in order of how common they are:**
1. **Scheduled (cron)** — simplest, fits well when documents change infrequently and predictably. A Kubernetes `CronJob` or a scheduled Azure DevOps pipeline running nightly/weekly would suit policy documents that update rarely.
2. **Event-driven** — triggered by an actual change: a new PDF landing in Azure Blob Storage (via Event Grid → Azure Function → ingestion job), or a policy-docs folder change merged via PR (extending the eval-gate pipeline concept you already have: PR changes a policy PDF → eval runs → on merge, ingestion pipeline re-indexes automatically).
3. **Manual/on-demand trigger** — a pipeline you kick off by hand when you know a document changed. Reasonable for a small team, less "production-grade" than the above two.

**What changes concretely in your project to get there:**
- The GUI's "Index Policy Documents" button becomes dev/demo-only — in a real deployment, it either goes away entirely or gets locked behind an admin-only path, never a general user-facing control.
- A separate, small entry point (could just be `python -m askhr.core.pipeline`'s ingestion half, wrapped as its own container command or Kubernetes `Job`/`CronJob`) becomes the *only* thing with write access to the vector store.
- The Streamlit app keeps `generate_answer()` but never calls `ingest_documents()` in the request path at all.
- Worth knowing as a real limitation, not solved yet: your current Chroma+PVC design is genuinely awkward for this model at real scale, because a `ReadWriteOnce` PVC only lets *one* pod mount it — so even with ingestion properly separated, you're still capped at one serving replica unless you either switch to `ReadWriteMany` storage or move to a managed vector DB (Azure AI Search, a hosted Qdrant/Weaviate, pgvector on Azure Postgres) that supports genuine concurrent reads from many stateless replicas while a separate job writes to it. That's the natural next architectural fork if this ever needs to scale past one pod.

One more thing worth naming even though it's not needed at your current scale: production systems doing this well also **version the index** rather than overwrite it in place — the ingestion job writes to a *new* collection, and only swaps the "active" pointer once the new build succeeds, so a mid-rebuild failure or a bad ingestion never leaves serving reading a half-written or empty index. Good to know the pattern exists; not something I'd build for a single-replica policy-PDF assistant today.

**Small step already taken in this direction:** the BM25 keyword index is now built once during ingestion and persisted to disk (`resources/vectorstore/bm25_index.pkl`), rather than rebuilt from the vector store on the read path at query time — see `HYBRID_SEARCH.md`. This is the same underlying principle as the write/read separation above, applied at a smaller scale: it does not yet separate ingestion into its own process/deployment, but it does stop one specific piece of "read-path" work from depending on corpus-wide computation happening inline with a user's request.
